# TopoRealm 图建模原则（机械）

本技能回答"结构怎么装进图"：kind 粒度、payload 形状、id 策略、数据纪律。
全部内容与具体业务无关——换任何题材，规则原样成立。动词语法（命令怎么敲、
旗标怎么写）见 `toporealm` 技能；本篇只讲取舍与归因。

建模决策对照的核心机制只有两条执法（core 只管这两条，其余都是模块钩子的事）：
**悬空边检查**与**所有权法**。下面的每条原则几乎都能追溯到它们或浅合并语义。

## 一、对象还是关系

- 名词性、独立存在、要被单独查询/更新/删除 → **对象**（`add`，有 kind + payload）。
  联系性、离开两端就没有意义、主要作用是连接 → **关系**（`link`，有 source/target）。
- 关系是一等实体：有自己的 id、kind、payload——不是对象的属性，也不只是边的装饰。
  联系本身的属性（次序、权重、方向语义）放关系的 payload：`link` 之后再
  `set <关系id> k=v` 追加。
- 判断"联系还是对象"的硬标准：**这东西要不要被第三方再连接**。
  要 → 升格为对象（用关系挂回两端）；只有端点访问它 → 保持关系。
- 方向是一条建模信息，不是两条边：`link` 的语义是 `source -> target`，谁指向谁
  要设计好。邻域读（`read <id>`）对相触关系是**双向**触达——不需要为"反向查询"
  再建一条反向边，一条边查两头都能出来。

## 二、kind 粒度

- kind = `<namespace>.<主类型>`（模块数据）；无点号 kind = 公共/无主类型。
- **一个 kind 承载一个概念**。kind 按"是什么"划分，不按取值划分——状态、
  归属、量级这类取值差异进 payload，不进 kind。
- 反面信号：同一批实体仅因某个属性不同就得用不同 kind；或者查同类得枚举一长串
  `--kind` 才凑得齐。
- kind 是词汇：一旦有数据入图，kind 实际上不可改名（改名 = 旧数据成孤儿）。
  建模期宁可少定 kind（payload 补细节），也不要广撒 kind。

## 三、payload 设计

- **`title` 约定**：每个对象放一个简短字符串 `title` 作为显示名。CLI 人类输出、
  画布显示都以它为显示键；模块可以用 `ui.titleKey` 指定别的键，但缺省就是
  `title`。没有 title 的实体在输出里只剩 id，人和画布都难认。
- **扁平化**：要把过滤、投影、单独更新的键放 payload **顶层**（标量或短值）。理由
  全在机制上：
  - `set` 是**浅合并**：只作用顶层键。嵌套对象作为整体被替换——不能只改深层
    一个键，必须整块重发（或 `--replace` 整体替换，需给完整载荷）。
  - `find` / `read --where` 匹配顶层键；`--fields` 投影顶层键（裸键 = `payload.<键>`）。
    埋深的键既筛不了也投不出。
  - 浅合并下的演化策略：加键直接 `set`；删键 `k=null`；改嵌套对象 = 整块重发。
    需要频繁局部更新的信息，别放嵌套结构里。
- **关系进 link，不进 payload**：两个实体之间的任何连接都建关系，
  不要在 payload 里存对方的 id 列表。机制后果（每条都是实打实的功能差异）：
  - payload 里的引用**没有悬空检查**——被引用者被 `rm` 后留下死指针，静默无告警；
  - 邻域读只沿关系触达，payload 引用读不出来；
  - 画布画关系，不画 payload 引用。
- **大体积内容不进 payload**：payload 只放需要过滤/投影/展示的小字段。大块内容
  放外部文件，payload 存路径或引用。每次 `read` 都全量携带 payload，巨型载荷
  拖慢每次读取并撑爆每笔提交的差异。

## 四、id 策略

- 两种来源：
  - **显式 `--id X`**：外部可预测、跨会话稳定、写入可重放。id 规则：禁
    `/ \ : ` 与控制字符、不得有首尾空白，且不得为 Windows 保留名；对象与关系共用一个 id 空间。
  - **匿名**：不给 `--id` 时 daemon 生成 `<主类型尾段>-<8位hex>`（如
    `thing-1a2b3c4d`）。格式带随机数，**事后猜不出来**——要用一律以回显为准
    （`--json` 的 `data.id` / `created`；别解析人类输出文本）。弄丢了就
    `find` / `read` 找回来，不要按格式拼。
- **幂等写入**：
  - `add` 带 `--id` 是 upsert（put 语义）：同 id 重放同载荷 = 整载荷覆盖，结果
    幂等——批量导入、脚本重跑安全。
  - put 是整载荷覆盖：**重放必须带完整载荷**，只带部分会抹掉其余键；局部更新
    用 `set`，重放场景用 put + 完整载荷，两者别混。
  - id 已存在且 kind 不同 → `UNKNOWN_KIND`（upsert 不改主类型；确要改先
    `rm`——有关系先删关系——再重建）。
  - 匿名 id 每次必新建：同一段不带 `--id` 的 `add` 跑两遍 = 两个实体。
    防重复就给显式 id，或写前先 `find` 确认。
- 选择标准：后续步骤要在**别的提交或别的会话**里按 id 引用它，或写入要可重放
  → 显式 id；一次性创建、当场用回显继续 → 匿名即可。

## 五、数据纪律（执法面与词汇面）

core 只执法两条，但它们直接约束建模；词汇纪律来自模块装载，同样是硬的：

- **悬空边**：`link` 的端点必须存在（可与端点创建放**同一提交**——创建先于建边
  生效）。`rm` 被关系引用的对象会被 `DANGLING_RELATION` 拦截（错误点名关系 id）。
  建模含义：删除顺序恒为"先边后点"，没有级联删除；删除路径要设计在数据流程里。
- **所有权法**：只约束模块来源（`module:*`）的提交——模块只能写自家
  `namespace.*` 或公共/无主 kind，跨 namespace 写入被 `OWNERSHIP_VIOLATION`
  硬拦。模块间协作的 sanctioned 模式是数据面：**读他人实体 + 在自家 namespace
  建关系指向它们**，不代写他人数据。
- **词汇只增不删**：模块声明的 kinds（objects/relations）只加，不改名不删。
  删词不会删数据——只会让存量数据失去词汇归属（目录投影消失，模块再也无法
  合法触碰它们）。给 kind 命名时按"将来永远在"的标准起名。
- **人工经 CLI 写入不受所有权法拦**（CLI 来源不在执法范围），但仍应优先走模块
  命令操作 `ns.*` 数据：模块命令带输入校验与缺省值，直接 `add <ns.*>` 绕过
  命令的输入契约，容易造出模块自己都读不懂的数据。

## 六、反模式清单

| 反模式 | 机制后果 | 正确做法 |
|---|---|---|
| payload 里存关系（id 列表/外键） | 无悬空检查、邻域读不通、`rm` 静默留死指针、画布不显示 | `link` 建关系 |
| 巨型 payload | 每次 read 全量携带、提交差异膨胀、where/fields 只吃顶层键 | 小字段进 payload，大内容外置存引用 |
| kind 爆炸（按取值/细分角色开 kind） | 词汇表只增不删地膨胀、查询要枚举 `--kind`、同一概念数据被切碎 | 取值差异进 payload；一个 kind 一个概念 |
| 跨 namespace 写入 | 模块来源被 `OWNERSHIP_VIOLATION` 硬拦；人工绕过命令契约造脏数据 | 读他人实体 + 自家 namespace 建关系；人工走模块命令 |
| 深层嵌套 + 局部更新 | 浅合并下嵌套对象整块替换，局部更新做不到 | 要局部更新的键拍平到顶层 |
| 改名既有 kind | 旧数据成孤儿（词汇只增不删） | 新 kind + 数据搬迁，旧词保留到数据清零 |

## 附：何时拆新 namespace / 新模块

- **写权需要**：某组 kind 需要模块程序化写入（命令/钩子），它就该归属那个模块
  的 namespace——所有权法以 namespace 划界，模块写不了别家的 kind。
- **演化节奏独立**：一批 kind 总是一起变（加键、改约束、加词汇），而别的数据
  不跟着动 → 它们是一个 namespace 的候选。
- **跨项目复用**：要被多个工作区使用 → 做成模块，`module add --global` 进全局池。
- **不要按形状细分**：namespace 是所有权与协调边界，不是分类学。"长得不太一样"
  不构成拆分理由——拆了之后 kind/命令目录碎片化，查询反而要跨 namespace 拼。
